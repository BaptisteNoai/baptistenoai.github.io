Règles contre LLM, mesurés sur 200 annonces annotées

Relier une annonce de vélo d'occasion au bon modèle d'un catalogue : un petit LLM local fait-il mieux qu'une règle simple ?

Nov. 2026 · projet personnel · Python, Ollama, Pydantic, FastAPI

+

Sur 100 annonces de test, la règle simple fait 75 % de bonnes réponses. Le LLM seul en fait 30 %.

Le problème

Les particuliers qui vendent un vélo électrique sur buycycle écrivent le nom du modèle à leur façon. Pour comparer un jour leurs prix à ceux du revendeur, il faut relier chacune des 1 856 annonces à l'un des 3 422 modèles-années de mon catalogue, ou dire qu'il n'y est pas.

La méthode

  • 200 annonces annotées par moi, avec une consigne écrite : le bon modèle, ou « aucun ».
  • Un découpage fixe : 100 annonces pour régler les méthodes, 100 mises de côté pour la mesure finale.
  • Quatre méthodes comparées : une baseline de similarité de chaînes (rapidfuzz), une règle qui exige les mêmes numéros de version (batterie et taille de roue ignorées), un LLM local qwen2.5:3b via Ollama dont la sortie JSON est validée par Pydantic, et un hybride où la règle propose et le LLM vérifie.
Ce que la mesure a montré

Le petit LLM échoue dans les deux sens. Quand il choisit parmi des candidats, il ne dit presque jamais « aucun ». Quand on lui demande seulement de vérifier, il répond presque toujours non : l'hybride ne retrouve plus que 14,3 % des annonces qui ont un modèle au catalogue.

Ce qui est livré

  • La règle de version est retenue comme méthode par défaut, servie par une API FastAPI, avec un Dockerfile.
  • Les réponses du LLM sont mises en cache, donc les chiffres se rejouent sans relancer le modèle. Un workflow GitHub Actions est écrit pour rejouer les tests et l'évaluation, et signaler une régression.
  • Limites : 100 annonces de test, un seul annotateur, un seul LLM et un petit. Le rapprochement n'est pas encore branché dans l'Observatoire.

Méthode de travail : la question, l'annotation, le découpage et l'interprétation sont de moi ; le code a été écrit avec Claude Code.

Observatoire du vélo électrique d'occasion

Combien perd un vélo électrique d'occasion par an et par kilomètre, à modèle égal ? Collecte quotidienne, dbt, régression.

Depuis oct. 2026 · projet personnel · Python, dbt, DuckDB, Parquet, pytest

+

À modèle égal, un vélo électrique perd 3,1 % de sa valeur par an et 3,0 % par 1 000 km.

Le pipeline

  1. Collecte quotidienne planifiéeFlux produits de 2 revendeurs (Upway, Tenways), un instantané Parquet brut par jour, relançable sans doublon.
    Relevé des prix neufsPages produit Upway, robots.txt respecté, reprise après interruption : 5 264 annonces couvertes sur 5 276.
  2. dbt + DuckDBStaging pour le nettoyage, puis marts (table de faits des annonces, dimension des modèles). 23 tests de qualité des données.
  3. AnalyseRégression à effets fixes par modèle, puis une formule d'estimation du prix de revente.

Pourquoi garder le brut : un nettoyage se refait, un historique de prix perdu ne se rattrape pas. Chaque choix est daté et justifié dans un journal de décisions.

−3,1 %par an, à modèle égal, par régression à effets fixes
−3,0 %par 1 000 km parcourus
12,7 %d'erreur absolue médiane de la formule de prix, sur 1 568 annonces de test
Le biais de la première mesure

Ma première mesure donnait −5,2 % par an. En la confrontant à une deuxième méthode, j'ai vu qu'elle mélangeait l'usure du vélo et la hausse des prix neufs d'un millésime à l'autre. Comparer au prix neuf du même modèle corrige ce biais.

Limites

  • Prix de revendeur (Upway), pas de vente entre particuliers : c'est ce que le projet de rapprochement prépare.
  • Le « prix neuf » est le prix catalogue affiché, pas le prix réellement payé.

Application de suivi financier multi-comptes

Mes comptes LCL et Trade Republic dans une seule base, où relancer un import ne crée jamais de doublon.

Depuis août 2026 · projet personnel · TypeScript, Next.js, Prisma, SQLite, Python

+

Un pipeline ETL complet, de deux établissements jusqu'à un tableau de bord, avec une base que j'ai modélisée.

L'architecture

  1. Extraction en PythonBibliothèques open source woob (LCL) et pytr (Trade Republic). Sortie dans un schéma JSON commun, validé par Pydantic.
  2. Transformation en TypeScriptMême schéma revalidé par Zod, normalisation, dédoublonnage, catégorisation par règles.
  3. SQLite, modélisée avec PrismaMigrations versionnées, montants en centimes entiers, contraintes d'unicité qui rendent les imports idempotents.
  4. API REST et tableau de bord15 routes Next.js aux corps JSON validés par Zod ; budgets mensuels avec alerte, décomposition intérêts/capital d'un prêt.
Le bug du double comptage

Certaines opérations LCL apparaissaient deux fois. En cherchant, j'ai vu que leur date change entre l'état « en attente » et l'état « validé » : pour la base, c'étaient deux opérations différentes. Je n'importe plus que les transactions comptabilisées.

Les autres choix

  • Une table de liaison entre dépenses et remboursements, même partiels, pour qu'un achat remboursé ne compte pas deux fois ; les virements entre mes propres comptes sont neutralisés.
  • Chaque correction manuelle de catégorie devient une règle, réappliquée aux opérations similaires.
  • Tests de bout en bout avec Playwright, lancés en local, et un journal des décisions techniques.

Méthode de travail : le besoin, les règles de calcul, le diagnostic des erreurs de données et les choix d'architecture sont de moi ; le code a été écrit avec Claude Code comme assistant.
